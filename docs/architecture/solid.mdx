---
title: Princípios SOLID
description: "Como os princípios da arquitetura SOLID são aplicados neste boilerplate."
---

Construir um SaaS escalável requer uma forte base arquitetural. Este boilerplate adere estritamente aos **princípios SOLID** para garantir que o código base permaneça manutenível, testável e fácil de estender à medida que a equipe cresce.

## 1. Princípio da Responsabilidade Única (SRP)

> *Uma classe ou módulo deve ter um, e apenas um, motivo para mudar.*

Nós aplicamos o SRP principalmente através da nossa **Arquitetura Orientada a Funcionalidades (Feature-Sliced)**:
- **`features/`**: Cada funcionalidade (ex: `landing-page`, `auth`) é auto-contida. A `landing-page` não sabe como a autenticação funciona, e a `auth` não se importa com a interface gráfica (UI) da landing page.
- **Micro-utilidades**: Arquivos como `shared/lib/utils/api-validation.ts` fazem exatamente uma coisa: validar parâmetros da API usando Zod. Eles não buscam dados ou lidam com respostas HTTP.
- **Componentes**: Os componentes de UI (como os em `shared/components/ui/`) são "burros" e puramente de apresentação. Eles apenas recebem propriedades (props) e renderizam a interface.

## 2. Princípio Aberto/Fechado (OCP)

> *As entidades de software devem estar abertas para extensão, mas fechadas para modificação.*

Nossa **Arquitetura de Pagamentos e Webhooks** é o melhor exemplo de OCP neste projeto:
- A lógica central para atualizar o nível de assinatura de um usuário vive em `shared/lib/payments/handle-event.ts`.
- Ela aceita uma interface padrão `SubscriptionEvent`.
- Se você deseja adicionar um novo gateway de pagamento (ex: LemonSqueezy ou Paddle), você **não modifica** o `handle-event.ts` principal. Em vez disso, você cria uma nova rota de webhook (`app/api/webhooks/paddle`) que mapeia o payload do Paddle para a interface `SubscriptionEvent` e o passa para o manipulador principal.

## 3. Princípio da Substituição de Liskov (LSP)

> *Subtipos devem ser substituíveis por seus tipos base.*

No contexto do React e Next.js, nós aplicamos muito o LSP na nossa Biblioteca de Componentes (`shadcn/ui` + `React Aria`):
- Todo componente base de UI (como `Button`, `Input`, `Card`) estende seu equivalente HTML nativo através do `React.HTMLAttributes<HTMLElement>`.
- Se você substituir um `<button>` padrão pelo nosso `<Button>`, a aplicação não vai quebrar. Ele aceita todos os atributos padrões (`onClick`, `disabled`, `aria-label`) perfeitamente, garantindo substituição sem atritos.

## 4. Princípio da Segregação de Interface (ISP)

> *Os clientes não devem ser forçados a depender de interfaces que eles não usam.*

Evitamos "Objetos Deus" (estruturas de dados gigantes passadas para todo lado).
- **Zod Schemas**: Definimos esquemas Zod estritos e segregados para endpoints específicos de API (ex: em `api-validation.ts`).
- **Props**: Os componentes React recebem apenas as propriedades específicas que precisam. Por exemplo, a `PricingSection` não recebe o objeto `User` inteiro; ela recebe apenas um array de planos `plans`.
- **Hooks**: Hooks customizados como `useLocale()` ou `useIsAdmin()` retornam apenas os métodos e booleanos específicos necessários para a sua tarefa isolada, em vez de retornar um objeto de contexto massivo.

## 5. Princípio da Inversão de Dependência (DIP)

> *Módulos de alto nível não devem depender de módulos de baixo nível. Ambos devem depender de abstrações.*

Nós isolamos as dependências de terceiros para que a aplicação central não fique fortemente acoplada a elas:
- **Autenticação**: A UI não depende diretamente da implementação do Better Auth. Ela depende de nossas abstrações (`shared/lib/auth-client.ts` e `shared/lib/auth.ts`). Se em algum momento nós migrarmos de Better Auth para outro serviço, só mudamos os arquivos `lib`; os componentes React permanecem intocados.
- **Ponte de Analytics**: `shared/lib/analytics.tsx` envelopa o PostHog, Microsoft Clarity, e GA4 por trás de um Provider Context unificado. O resto do aplicativo apenas dispara eventos genéricos sem saber *qual* ferramenta de métrica está os recebendo.
- **Banco de Dados (Supabase)**: O acesso a dados é abstraído dos componentes de UI. Nós injetamos o contexto do cliente do Supabase ao invés de importar instâncias globais diretamente nas camadas de visualização.
